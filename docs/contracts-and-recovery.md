# Execution contracts and recovery

This document describes the implemented single-owner controller and the second-increment bounded coordination contracts. Orca remains authoritative for Runs, Tasks, Dispatches, dependencies, gates, workers, messages, and terminal ownership. The local database is an effects journal and evidence index, not a task scheduler.

## Project and source binding

`orchestrate setup` performs bounded name discovery and writes `.orchestrate.json`. It does not run setup hooks, tests, build commands, or model calls. The v1 profile contains only repository-relative references, optional explicitly selected `candidateSources`, the reader kind, check commands, and the `single-owner-first` preference. The explicitly authorized initial setup action also records those exact bytes in a host-local `orchestrate-operational-profile-selection/v1` history outside the project. This is an operational configuration selection, not CE-GD or project-governance approval.

Neither Git `HEAD` nor a commit is an approval source. If candidate profile bytes differ from the selected digest—even after commit—mutating commands hold. After reviewing a deliberate change, `orchestrate setup --acknowledge-profile` appends the exact source bytes, digest, time, and acknowledgment source to that host-local history and selects the digest. It also appends explicit acknowledgment when the candidate digest is unchanged but the active selection has only initial-setup provenance. Missing, malformed, or internally inconsistent selection history holds; it is never recreated implicitly by `implement` or `resume`. Repository instructions and governance remain authoritative for scope, checks, review, and acceptance.

Before task creation, the reader records exact Git HEAD/tree/branch and a digest of the complete porcelain status without opening every changed path. One case-sensitive Git pathspec-filtered inventory includes at most 256 tracked and ordinary untracked files at any depth having the exact conventional `AGENTS.md` or `CLAUDE.md` names; ignored files are excluded, and an oversized or non-UTF-8 inventory holds. Every selected instruction absent from that current inventory—including a legacy selection or a path hidden by a later ignore rule—holds at profile load and is rechecked on reader and source-index entry before any selected instruction bytes are read or hashed, unless the active selection has explicit-acknowledgment provenance. The operator cure is to review the unchanged profile and run `orchestrate setup --acknowledge-profile`; an ordinary startup records no acknowledgment. Reader instruction authority is then the deterministic union of the conventional inventory and selected `instructions`, with every member read through the same safe source boundary and represented in reader instructions, consulted paths, and authority routing. Managed preflight treats every packet source with a conventional instruction base name, as well as every selected instruction, as instruction-class. If such a packet-carried source is no longer conventional and is not both explicitly selected and acknowledged, preflight holds with `instruction_acknowledgment_required` before reading that source or performing a native Orca readback; an unselected packet source must first be deliberately added to `instructions` before the setup acknowledgment can authorize it. The source index records SHA-256 identities only for configured, inventoried, or reader-routed non-secret sources and operationally selected `candidateSources`; for a staged consulted source, worktree, index, and HEAD identities remain distinct. Dirty paths outside that bounded set remain path/status-only `uncoveredChanges` and hold dispatch until the selected profile or exact routing covers them.

Conventional credential stores and names, environment files, and private-key/certificate suffixes are excluded even if named in `candidateSources`. POSIX reads traverse directory handles with no-follow flags. Windows opens the target with reparse-point semantics, verifies that the opened final identity is exactly the intended in-root path, denies concurrent writers for the bounded read, and consumes bytes from that same handle. A changed or new candidate instruction can restrict work but is not treated as a new authority grant.

The CE reader does not infer a `.ceip.json` interface. It requires exactly one task matching `CE-` plus exactly four digits in the objective, resolves that task through `docs/tasks/README.md`, and follows the task's required Context packet links. Project logs use only the observed `ce-systems-project-log-manifest` schema v1: shard metadata selects every declared shard whose `task_ids` contains the exact task, so multiple declared shards are legitimate and unrelated siblings are excluded.

Shard contents are not opened generically. When the selected operational profile includes `package.json`, the manifest advertises the exact query interface, and the clean tracked package script maps exactly to `node scripts/quality/project-log.mjs query`, the reader invokes `pnpm --silent run project-log:query -- <exact-task> --json --max-entries 12 --max-bytes 32768`. Strict JSON must echo the task, list exactly the manifest-selected shard paths, and return only typed matches from those shards. Any unknown schema, dirty query source, cross-task result, malformed response, timeout, or nonzero `omitted_matches` holds. Managed preflight first decodes the bounded canonical v3 packet and every mandatory field of every exact source-index/v1 record inside the admission/effect fence, before it loads profile source bytes, reads any packet source, runs Git, or performs native Orca readback. One in-memory eligibility model then binds each path's profile, instruction, task-entrypoint, command-manifest, candidate, reader-routed, and controller-bound milestone-plan membership to either reference-only, direct-byte, or inventory-guarded access. Milestone membership comes only from the host-local plan binding used by the controller; a packet path or filename cannot invent it. Repo-reader routing must already agree with profile/instruction membership and cannot grant a byte read by naming an extra path. Directly eligible sources—including explicitly acknowledged selected instructions—are compared first, preserving their pre-subprocess rejection guarantee; the single bounded conventional-instruction inventory then authorizes the remaining instruction reads and supplies the one rebuilt source index. A source classified reference-only remains unreadable for the complete stage: if it appears after its first absence check, validation rejects without opening its bytes. Missing sources, selected/discovered ignore transitions, and acknowledgment provenance are therefore decided by that completed model rather than reconstructed by later stages. Native readback and the reader consume the completed packet and source results; the reader does not rebuild the index or reopen captured text for routing. This intentionally removes the earlier second byte hash performed by index construction; Git state and identity fields are observed later, but bounded multi-file reads are not an atomic snapshot. The effectful CE query consumes the completed package, query-script, and manifest identities and rechecks those exact identities immediately before and after its subprocess. All admission-held Git calls have bounded output and a 30-second timeout. The exact query result is hashed into routing. This is the one bounded machine interface, not authority to run arbitrary candidate scripts. These internal changes preserve the exact `orchestrate-worker-packet/v3`, `orchestrate-source-index/v1`, and `orchestrate-worker-preflight/v1` wire identities.

The compact `orchestrate-worker-packet/v3` is stored outside the repository and binds the objective, native Run, starting candidate, operational-profile selection provenance, source identities, reader routing, required checks, owner launch identity, exact isolated package interpreter, outputs, and unresolved limitations. Task creation necessarily precedes a native Task ID, so one canonical JSON byte representation is finalized once, persisted unchanged, and embedded byte-for-byte in the Task spec; it says that Task/Dispatch identity comes from Orca's injected dispatch preamble and does not fabricate a pre-create Task ID. Pre-canonical local rows retain their historical compact JSON bytes and are never silently rewritten; recovery derives canonical bytes in memory but gains no proof unless exact native Task-spec readback succeeds. Legacy packet versions cannot grant a new admission. `packet` still requires the exact locally bound Run and Task to retrieve that immutable document.

Task titles are bounded display metadata, not a substitute for the objective or immutable packet. Before `task-create`, the controller applies the observed Orca 1.4.198 single-line normalization: ECMAScript whitespace is trimmed and collapsed, values longer than 80 UTF-16 code units use at most 77 units plus `...`, boundary whitespace is removed, and a surrogate pair is never split. An all-normalization-whitespace edge uses the literal `orchestrate task`, so Orca never silently derives display metadata from the packet spec. New Tasks receive that already-bounded title. Task readback and resume require the exact deterministic title as well as the exact Run ID, Task ID, packet spec, and admissible pre-dispatch status, so an Orca-normalized Task created before controller interruption is reused rather than replaced.

## Host-local records

State lives beneath the operating system's local state directory, or `ORCHESTRATE_HOME` in disposable tests. Before creating a selection, database, packet, or lock, orchestrate rejects a target lexically or physically inside the project, a Windows UNC target, and positively identified OneDrive, Dropbox, Google Drive, iCloud Drive, Box, or Syncthing roots. This is a bounded detector, not proof that every proprietary, redirected, remotely mounted, or synchronized filesystem can be identified; operators remain responsible for choosing a private host-local root. State is keyed by a normalized project-root digest and contains:

- append-only operational-profile selection records with exact source bytes and digests;
- local-to-native Run bindings;
- mutation intentions, exact subprocess exit statuses, and public request receipts;
- immutable validated worker-resource bindings for resource ID, terminal handle, and worktree ID;
- immutable whole Delivery responses plus per-message effects;
- exact worker packets;
- immutable conclusive passed or rejected worker-preflight observations plus append-only failed-attempt observations;
- exact milestone-plan, native Task/dependency, gate, worker-session, and result bindings;
- questions and answers; and
- worker claims and other evidence with their stated status.

A non-blocking OS file lock fences two local controllers for the same Run. It does not claim to lock unrelated humans, agents, worktrees, or remote hosts.

## One-worker state machine

The normal sequence is `run-create`, exact Run readback, `task-create`, exact immutable-spec Task readback, last pre-call source validation, `worker-start`, exact Dispatch/worker/resource readback, `awaiting_preflight`, joined admission, `waiting`, foreground `check`, full Delivery journaling, message effects, native settlement readback, worker release, and whole-Delivery acknowledgment. Every orchestration mutation receives a durable intention before the public Orca call. Orca 1.4.198 and 1.4.199 use exit 0 for `worker-start` `ready`, and deliberately use exit 1 for `failed` or `outcome_unknown` even though that structured command envelope remains `ok: true`. The strict subprocess client retains the exit status; only the exact exit-1 failure/unknown combination reaches controller validation. A ready result with nonzero status, a failed/unknown result with any unexpected status, and every other nonzero combination fail closed across fresh and recovery paths. `ready` at `input_accepted` is input-acceptance evidence, not proof of a started model turn and not source admission. The version-keyed accepted-worker validator additionally requires null Dispatch failure and worker error fields, the immutable Run/Task/Dispatch/worktree/terminal/resource identity, and an initially owned resource whose release has not been requested. Worker-start readback, managed preflight, the bounded submission diagnostic, admission, and the active doctor all use that same validator. If foreground supervision ends while the exact preflight remains absent, the controller performs one read-only, Dispatch-bound `worker-show` observation. An unchanged `dispatched`/`ready`/`input_accepted` worker and exact terminal-resource identity produces one unresolved `worker_input_submission_unproven` compatibility record. That record causes no task-text resend, Enter key, replacement launch, release, or other external effect.

Before edits or project checks, the worker runs the packet's exact `python -I -m orchestrate worker-preflight ...` command, which validates native actor/Run/Task/Dispatch/runtime/workspace/model and canonical packet identity plus freshly observed selected-profile/source/routing identity. Native Windows requires the actual Python platform to be `win32`, the packet interpreter to be that exact Python, `terminal.executionHostId=local`, the exact live terminal/agent/worktree identity, and one runtime identity across all readbacks. Orca 1.4.199 may omit `terminal.hostPlatform`; omission is accepted only with that joined native/local proof. A reported platform must be exactly `win32`, while missing or non-local execution-host identity, a reported non-Windows platform, runtime drift, or workspace/actor mismatch rejects. The observation records the controller platform, the reported terminal platform without inventing an omitted value, and which proof path was used.

Once the selectors identify an existing local attempt, every ordinary exception from packet decoding through source/routing validation and native readback is contained inside the admission/effect fence and first produces an append-only failed-attempt `orchestrate-worker-preflight/v1` observation. Semantic contradictions and unexpected contract exceptions are definitive: they additionally occupy the Dispatch's immutable conclusive rejection row, so exact restoration cannot issue a fresh editing grant. A genuinely missing or changed packet-bound source is definitive, including a mandatory CE query source removed from the Git index after the completed source stage. Git blob inspection treats an object as absent only after a separate successful Git listing proves that absence; a nonzero object-read command for a still-listed source is an environmental inspection failure instead. Bounded environmental availability failures—an unavailable Git/Orca/query subprocess or a safely identified source that is still present but temporarily cannot be opened—are retryable: their failed-attempt observation remains durable, the conclusive slot remains empty, and the same Dispatch may run preflight again after the environment recovers. Retryable does not mean admitted, does not authorize edits, and does not clear or overwrite its earlier attempt history. Process-control exceptions such as `KeyboardInterrupt` and storage failure while recording evidence remain outside this application-level distinction.

A definitive rejected, malformed, or launch-conflicting observation moves any question-bearing nonterminal or blocked local Run to `preflight_held` without deleting its question, escalation, or Delivery evidence; `implement`, `resume`, and `answer` surface its exact admission detail before ordinary lifecycle effects. Pending admission, including a retryable attempt with no conclusive observation, similarly reports a preflight/recovery obligation before any answer-question instruction. The exact worker resource binding and single-writer ownership remain preserved, and definitive disposition requires a separately authorized cleanup path. Status and explain expose the conclusive rejected observation's mismatch code, message, and bounded field details. An observation may precede controller receipt processing, but only an exact conclusive pass joined with the validated launch advances to `waiting`.

A dedicated host-local Run-scoped admission/effect fence is distinct from the broader controller Run ownership lock. It uses a bounded OS-lock acquisition, and the operating system releases it if its owning process exits. Public `worker-preflight` holds the fence from exact existing/foreign observation inspection through validation and immutable observation insertion. `answer` holds the same fence from joined-admission validation through reconciliation, native Run binding, reply, local question/message updates, and Delivery acknowledgement. Resume retry/reconciliation and post-check Delivery processing/release/acknowledgement use the same admission-ordered intervals. `worker-start` does not hold this fence because the first worker preflight may need to complete before that public call returns; a foreground check may likewise wait while first admission is still pending, but after the check returns the controller acquires the fence and rejoins admission before any Delivery or diagnostic effect. Thus a later managed preflight observation is either visible before a controller interval and holds it, or is inserted only after the complete interval ends. Once the controller binds a Dispatch, every immutable observation for the same local Run/Task is enumerated: an observation recorded under a different Dispatch, or more than one observation, is `conflicting`, and no subsequent managed diagnostic, Delivery, reply, release, acknowledgement, or retry effect begins after that row is inserted. Status/explain list those other-Dispatch observations beside the bound Dispatch. A worker preflight for a second Dispatch of a Run/Task that already holds an observation is rejected without native readbacks; prior observations are never overwritten or cleared. The fence orders only these managed admission/effect paths; it is not enforcement against a hostile preflight bypass or an unrelated external writer.

This preflight is a managed protocol and durable provenance observation, not an arbitrary-shell enforcement boundary. It does not prove that a hostile worker avoided earlier edits, exclude later external writers, or make bounded multi-file reads atomic. Managed active or uncertain attempts retain single-writer ownership. Source/profile changes after admission are treated as possible output for lifecycle and cleanup; they are not rescanned as starting proof and never authorize duplicate launch. `worker_done` without joined admission preserves the native outcome and cleanup evidence as `worker_unadmitted`, with verification `not_run`; worker prose cannot supply admission, and the CLI returns a nonzero exit both directly and through ordinary-terminal bootstrap.

Only one new active local objective is admitted. `worker_done` must bind the exact Task and Dispatch and match native Task/Dispatch settlement. A succeeded worker is recorded as a worker claim with independent verification still `pending`; it never becomes acceptance or release proof. Failed workers are released and remain failed.

Every original FIFO element must be an object, and the exact whole Delivery response is durably journaled before parsing or effects. For Orca 1.4.199 current Delivery rows, `run_id`, `delivery_contract=current_delivery`, `from_handle`, `to_handle=run:<exact-run>`, and the raw `payload` JSON string remain version-bound wire fields; they are not broadly normalized. The payload must decode as one JSON object with no duplicate keys or competing snake/camel identity aliases and must bind the exact `taskId` and `dispatchId`. Questions require `from_handle=dispatch:<exact-dispatch>`; heartbeats, escalations, and completion reports require the exact initially bound worker-terminal handle. Wrong Run, Task, Dispatch, destination, contract, sender, malformed JSON, non-object JSON, duplicate keys, alias mixtures, unsupported mail, and unresolved escalation all hold the journaled Delivery unacknowledged. Questions keep the entire Delivery unacknowledged until `answer` durably replies.

Release is accepted only from an exact Dispatch-bound mutation response plus structured `worker-show` readback. The controller first persists the terminal resource ID, terminal handle, and worktree ID from the validated initial worker readback; every post-release readback must match all three immutable values as well as the Run, Task, and Dispatch. Worker execution and terminal-resource disposition are separate state dimensions. For both supported identity encodings, an ordinary success must remain `completed`/`succeeded` at worker stage `settled` with null failure/error, an ordinary `worker_done` failure must remain `failed`/`failed` at stage `settled` with `worker_failed`, and a historically failed prompt start must remain `failed`/`failed` at stage `dispatch_input` with `agent_prompt_stalled`. In every case the worker record retains its exact original agent-terminal handle; releasing the resource does not rewrite the worker's historical execution stage or identity. A released owned terminal separately requires `ownershipState=releaseState=released`, null reason/error, exact origin/owner IDs and immutable resource/terminal/worktree IDs, timestamps, a captured transcript archive, and no attached top-level terminal. `released`, idempotent `already_released`, and a previously stored `release_pending` receipt may converge only against that same semantically consistent released readback. A documented `release_pending` response is an unresolved transition: its full recovery metadata remains in the applied intention, restart performs only the exact `worker-show` readback, and a still-pending or semantically contradictory resource remains cleanup-pending without another worker start, a replacement release request, or terminal close. Prior release with retained user ownership requires `ownershipState=user_owned`, `releaseState=retained`, `retainedReason=user_takeover`, null release timestamps/error, and null archive fields; the worker itself must still have the exact settled execution semantics and original terminal handle. Retention is not a safe disposition for an `agent_prompt_stalled` failure: that path remains `launch_cleanup_pending` until the exact owned terminal is positively released, then becomes `worker_failed` with verification `not_run`. Opaque prose, unknown fields, external retention, and unobserved dispositions such as `no_owned_resource` remain unresolved. A Delivery is acknowledged only after every journaled message has a resolved effect and release disposition and `check --ack` returns `result.acknowledged` equal to that exact requested Delivery. Missing, null, malformed, competing, or different acknowledgement identities never make the intention applied or the local Delivery acknowledged. Any distinct well-formed next FIFO Delivery returned by the same response is journaled before it becomes the bound Delivery; otherwise it is left without effects for Orca to replay. Worker evidence, the terminal Run phase, and the message effect are one local SQLite transaction, and an unacknowledged terminal-phase Delivery remains resumable and is replayed before return.

## Interruption and uncertainty

Ctrl-C stops foreground controller waiting and does not kill a worker. `resume` first takes the same host-local lock, reapplies locally committed receipts idempotently, and inspects unresolved native mutation request identities. The retry identity is Orca's `result.mutation.requestId` (or its documented error-data mutation receipt), never the top-level transport correlation ID. `request-show` must return that exact ID, the expected method, timestamps, receipt, and interpretation. A `completed` or `pending` public request is replayed only with that exact `--retry-request` identity. Delivery-ack recovery applies the same exact acknowledged-Delivery validator to a retry receipt and to an already applied receipt before committing local ack state; stored argv alone is never acknowledgment evidence. An absent or missing receipt remains `unknown_external_effect`; absence never authorizes a fresh attempt. A recovered worker-start receipt still undergoes the same effective-launch and `worker-show` checks before the local phase can become `waiting`.

The bounded `agent_prompt_stalled` recovery is stricter because Orca has already created and injected into a supervised terminal before it settles the Dispatch failed. The controller requires exit 1 plus the exact failed `dispatch_input` receipt, requested/effective launch, three effects, single residual agent terminal, failed Dispatch/worker readback, start options, and Dispatch-owned terminal resource. It immutably binds that resource's ID, terminal handle, and worktree ID to the failed Dispatch, records `launch_cleanup_pending`, and invokes only the supported idempotent `worker-release`; it never sends a manual proceed prompt or silently starts/retries another worker. On restart, the exact `ok: true` failure receipt that the earlier client stored in an uncertain intention is recovered directly without replaying `worker-start`, and an already applied released or pending release is only read back rather than reissued. A legacy applied prompt-stall start can deterministically reconstruct a missing local resource row only by revalidating its exact stored start plus the same Dispatch-owned resource readback.

`worker-show` identity and execution parsing is explicitly bounded to the two installed public shapes. Orca 1.4.198 requires `run_id`/`task_id`/`last_failure` on Dispatch and `worktree_id`/`agent_terminal_handle`/`last_error` on worker, while rejecting the corresponding camel-case aliases. Orca 1.4.199 requires `runId`/`taskId`/`lastFailure` and worker `dispatchId`/`worktreeId`/`agentTerminalHandle`/`lastError`, while retaining an equal Dispatch `task_id` compatibility field and rejecting `last_failure` plus the other snake-case worker aliases. Each version has an explicit positive table for ordinary success, ordinary failure, and prompt-stall execution correlations; the values currently agree across the two versions, but neither version inherits an open-ended alias or stage set from the other. Mixed, conflicting, incomplete, or unenumerated shapes fail closed; this is not general key normalization.

Source changes or incomplete selected candidate coverage before a genuinely new worker launch stop the state machine. Once launch may have occurred, recovery reconciles that exact intention and admission without rereading output into a fresh grant or issuing a duplicate launch. Omitted Run IDs are accepted only when selection is unambiguous.

## Bounded native DAGs and review gates

The default `implement` and `resume` path remains the first-increment single owner. The second-increment production path is selected only by `implement <exact-objective> --plan <tracked-project-relative-json>`; `resume --plan` may reassert only the already-bound path. The file must be strict `orchestrate-milestone-plan/v1` JSON with exactly `schema`, `contract`, `maxWorkers`, and `tasks`. Each Task has exactly `key`, `title`, `spec`, `role`, `dependencies`, and `gate`. The owner spec must byte-for-byte equal the authorized CLI objective and own the sole `integration` gate. At least one specialist owns a `verification` gate, exactly one final reviewer owns the `review` gate and depends on every specialist, and the complete plan is bounded to twelve Tasks and at most eight concurrent workers. Unknown fields, an untracked plan, a changed bound plan, a second owner/reviewer, cycles, overlapping contract writers, or invented role/gate associations fail closed.

```json
{
  "schema": "orchestrate-milestone-plan/v1",
  "contract": {"interface": "frozen-v1", "checks": ["focused"]},
  "maxWorkers": 2,
  "tasks": [
    {"key": "owner", "title": "Integrate", "spec": "Integrate the exact bounded milestone", "role": "owner", "dependencies": [], "gate": "integration"},
    {"key": "verify", "title": "Verify", "spec": "Run focused read-only verification", "role": "specialist", "dependencies": ["owner"], "gate": "verification"},
    {"key": "review", "title": "Review", "spec": "Independently review the exact candidate", "role": "reviewer", "dependencies": ["owner", "verify"], "gate": "review"}
  ]
}
```

The owner still runs through the established first-increment packet, admission, supervision, settlement, release, and acknowledgment path. Only after that exact owner succeeds does the controller recapture the candidate, settle the plan's canonical shared-contract bytes, and create follow-up Orca Tasks in topological order. The contract retains no caller-owned mutable container: its digest is recomputed from the exact canonical nested JSON, and each access returns a deeply immutable tree. Every follow-up Task and packet is bound to that contract digest and the post-owner candidate digest.

Dependency keys are serialized to exact native Task IDs with `task-create --deps`; `task-list` readback must retain Run, spec, dependency, and state, and every row in `task-list --ready --brief` must remain an exact bound Task. Before truncating for remaining capacity, the controller joins the complete ready view against all locally active and finished milestone Task identities. A native ready row for either set is contradictory and holds; otherwise the controller orders the eligible frontier by the immutable plan and starts only the deterministic prefix that fits `maxWorkers - activeWorkers`. Later valid Tasks remain native-ready and enter subsequent waves after capacity is released, including after controller restart. Verification and review labels also create real native gates. Gate creation and resolution are intention-journaled and checked through exact `gate-list` readback. If a response is lost, a single exact live gate plus the stored request identity may recover the projection; ambiguity, missing request identity, or a conflicting Task/question/status/resolution prohibits a duplicate mutation.

Verification gates open only after the settled owner candidate has been frozen. The final review gate remains pending until every specialist has exact joined preflight admission, matching native Task/Dispatch settlement, and a strict host-local `orchestrate-milestone-result/v1` file whose Task, Dispatch, candidate, contract, and `accepted` outcome match its immutable packet. Result reads use the same no-follow, handle-based boundary as project sources. Prose, `worker_done` alone, missing/malformed files, wrong identity, failed native settlement, or a `rejected` outcome cannot open a later gate. The exact final reviewer must meet those same conditions; its accepted result is then checked against the exact planned review Task and current candidate/contract before local verification becomes `review_accepted`.

`status` and `explain` first select the exact stored Run through an existing-database-only StateStore opened with SQLite `mode=ro&immutable=1` plus `query_only`. Reporting creates no directory or database, performs no DDL, migration, metadata replacement, or WAL checkpoint, and refuses both a snapshot with live SQLite sidecars and any database whose required current table-to-column contract is incomplete. Missing-column failures occur at open with `state_schema_migration_required` and exact `table`/`missingColumns` evidence, before any report route can index a row.

Milestone reporting is selected from the stored Run lifecycle and any milestone-specific plan, Task, gate, or worker history; it does not depend on the nullable plan projection row alone. After accepted review, exactly one plan row must remain. Before any packet is consulted, its JSON must be the canonical `orchestrate-milestone-plan/v1` bytes, its plan digest must recompute, its candidate and deeply validated settled-contract digests must agree, and its complete Task roles, dependencies, gates, and immutable native Task/worker/resource readbacks must match the stored plan. The existing intention journal must also contain exactly one applied creation receipt for the integration-owner Task and for every specialist/reviewer Task. Each receipt is joined to the exact native Run and Task IDs, unique native request identity and runtime response identity, production-normalized title, exact spec, and exact serialized dependency argv; malformed, reformatted, missing, duplicate, unapplied, altered, conflicting, or unbound creation history fails closed. Such plan or native-history failures project `stale_review`/`review_stale`, keep acceptance only under `staleEvidence`, and exit nonzero; neither the Run's earlier source digest nor packets are fallback authority. A missing, malformed, unreadable, or reparse-blocked current profile produces the same unavailable-current-identity projection. Without milestone history, profile failures retain the ordinary blocked result. Only exact identity restoration can make the historical acceptance current again.

Only after that stored plan identity passes does current candidate reconstruction use the normal canonical v3 packet validator for every expected milestone packet, then join each unique packet and packet ID to its exact plan row, native Run and Task, admitted Dispatch, stored worker resource, candidate and settled contract, and workspace root. Expected packets must agree byte-for-byte on profile, source identities, candidate, and reader routing. A malformed or noncanonical packet, invalid `packetId`, duplicate source or packet identity, conflicting expected packet, missing bound packet, or unbound packet row makes current identity unavailable. Staged, unstaged, untracked, deleted, or replaced consulted sources likewise immediately project the old acceptance as stale evidence and require a new exact-candidate review. Mutating continuation retains the separate pre-effect stale-candidate hold. A rejected or stale review is historical evidence and leaves a nonzero result. External acceptance, merge, and release remain separate.

## Role roster and effective launches

The role roster lives only in the host-local `orchestrate-user-config/v1` file. It has exactly `owner`, `specialist`, and `reviewer` slots. The reviewed defaults are Codex `gpt-5.6-sol` at high effort for owner/specialist and xhigh for the independent reviewer. A slot may instead name `claude` only with an explicit user-provided provider model ID; no provider lookup or availability guess occurs. Effort is optional for a configured provider ID and is never sent alone.

```json
{
  "schema": "orchestrate-user-config/v1",
  "roles": {
    "owner": {"agent": "codex", "model": "gpt-5.6-sol", "effort": "high"},
    "specialist": {"agent": "claude", "model": "user-configured-provider-id"},
    "reviewer": {"agent": "codex", "model": "gpt-5.6-sol", "effort": "xhigh"}
  }
}
```

Each worker start constructs arguments only from the selected role and then requires the complete `launch.requested` and complete `launch.effective` maps both to equal that exact selection. Missing effective capability, additional effective model/effort fields, aliases, or substitution cannot be projected away. Missing capability is `worker_launch_unsupported`; any difference is `worker_launch_mismatch`. Neither configured nor requested values are execution evidence by themselves.

## Session ownership and uncertain WSL release

Every accepted settled worker gets exactly one next session action before acknowledgement. Immediate follow-up work may reuse the same proven agent terminal only for the same agent and by both the exact captured handle and `--worktree id:<captured-worktree>`. Otherwise cleanup is `worker-release --dispatch <exact-id>`. Session readback composes the same installed-version execution validator used by the first-increment controller with exact Dispatch, Run, Task, worktree, original worker-terminal handle, and immutable resource identity.

`released` and `already_released` settle cleanup only when readback also proves the outcome-specific worker execution, released ownership/release state, null reason/error, request/completion timestamps, captured transcript archive, and null attached terminal. Explicit `user_takeover` retention remains distinct and requires its exact null timestamp/archive fields. `release_pending` and `release_unknown` are uncertainty, including the observed WSL shape. They must say `processAction=none` and carry a literal non-empty recovery description or argument array. orchestrate preserves that immutable recovery metadata and records `repeat_release=false`: no terminal close, locally reconstructed command, path re-resolution, or unchanged release retry is authorized.

## Intervention record

A repeated correction is keyed to its Task and proposed correction. Its durable record contains the current obligation, concrete failing example, hypothesis, last meaningful evidence, and next discriminating check; an incomplete record is rejected. A first correction or a correction supported by a different evidence digest may proceed. The same correction against the same evidence consumes exactly one bounded diagnosis. Completion runs in an immediate SQLite transaction and compare-and-swaps only a still-`required` row, so concurrent callers can receive at most one productive correction authorization. If that diagnosis produces genuinely new evidence, one correction may proceed; otherwise the state becomes an unresolved decision and further identical correction or diagnosis requests remain held.

## WSL forwarding boundary

The `orchestrate-wsl` entry point is transport, not a Linux controller. It requires a real `WSL_DISTRO_NAME` and one host-local `ORCHESTRATE_WINDOWS_COMMAND_JSON` argument array, then encodes schema, distro, absolute Linux cwd, and argv as canonical UTF-8 JSON inside a bounded base64url token. It launches that exact Windows command without a shell, inherits standard streams, and returns the exact Windows exit code. Empty argv, NULs, relative/traversing cwd, malformed/oversized/non-canonical payloads, a non-WSL sender, or a non-Windows receiver fail closed.

The Windows receiver reconstructs only the explicit `\\wsl.localhost\<distro>\...` path, marks the forwarded context, and enters the canonical Windows CLI. Therefore Windows `LOCALAPPDATA` remains the sole default state owner; the Linux launcher never imports or opens `StateStore`. Distro/cwd transport is not worker placement. Orca must still select and prove the WSL execution host and owns all worker commands, terminals, and release recovery. No live WSL lifecycle was exercised for this candidate.

## Ordinary-terminal bootstrap

When invoked outside Orca, mutating commands create one focused ordinary Orca terminal in the exact project worktree. An existing caller is accepted only after exact `terminal show`, `worktree current`, `worker-list`, and `run-current` readback proves an ordinary terminal in the requested worktree with no active or context-only Dispatch; hook credentials alone do not indicate an agent. The inner Python process owns Run authority.

The outer launcher uses the controller package's exact interpreter with isolated mode (`-I`) so a project `orchestrate.py`, `PYTHONPATH`, or user site cannot replace the helper. It durably journals its exact arguments and result path before terminal creation, then separately journals create, interrupt, exit, close, and report phases. Orca 1.4.198 terminal create/send/close responses do not expose a mutation request identity, so create uncertainty still holds and no uncertain mutation is repeated. An uncertain close may reconcile read-only only when the same runtime proves the exact handle exited with the stored exit code, the durable child result agrees, historical `terminal show` matches the stored handle/tab/incarnation/workspace/execution host and is disconnected/non-writable, and a complete exact-worktree inventory proves both terminal and tab absent. The create receipt must prove the local `win32` host platform; Orca 1.4.198 omits `hostPlatform` from historical `terminal show`, so that readback may omit the field but must echo the exact created platform if the field is present. Exit codes, inventory counts, and topology revisions used for that proof must be JSON integers; booleans are rejected even though Python otherwise treats them as integer-shaped values. Incomplete inventory, unknown layouts, runtime or identity drift, and missing child results hold. The failed close attempt remains historical evidence; reconciliation records a distinct observed-exited-and-absent disposition and never infers that close did not occur.

The bootstrap refuses to run from a reasoning-agent terminal, so a dispatched worker cannot use it to route around Orca's dispatch-depth rules. The transport-only WSL forwarding boundary is separate from bootstrap; a WSL-native worker lifecycle remains a live gate.

## Verification boundaries

The unit and incident suite uses disposable Git repositories and synthetic public-command responses. The Windows workflow job runs the complete suite, including fixtures whose intended assertions require native-Windows managed admission. The Linux job runs the host-neutral subset and explicitly skips only those native-admission-dependent tests because managed worker preflight is win32-only by design. Both jobs run explicit incident discovery, build a wheel, install it into an isolated environment, and run command smoke checks; the workflow definition alone is not hosted proof. The production CLI/controller milestone path, native-DAG/gate projection, release uncertainty, role, intervention, and WSL transport contracts have local synthetic coverage on their supported test hosts. Live Orca multi-worker/gate execution, real WSL worker lifecycle, model/provider behavior, hosted CI, independent candidate review, external acceptance, merge, release, and publication remain separate evidence unless explicitly exercised. See [Validation evidence](validation.md) for the evidence fields, gate matrix, and read-only/live boundaries.
